# 05 — PLAN.md Review Against Research

Date: 2026-10-16

This review compares `docs/v2/PLAN.md` with the research reports (`01-app-audit.md`, `02-mobile-stack.md`, `03-design-skills.md`, `04-ux-direction.md`). Each item includes a file:section reference and a suggested fix.

## 1. Contradictions Between PLAN.md and Reports

| # | Contradiction | Reference | Suggested Fix |
|---|---|---|---|

This is feasible only with aggressive route-level code splitting and lazy-loading MapLibre; PLAN.md treats it as a straightforward acceptance criterion without acknowledging the magnitude of the refactor needed. | PLAN.md: D1, §6; 01-app-audit.md: §3.3 | Reframe the 150 KB gz budget as a stretch goal with a phased path (e.g., establish baseline after W0, enforce budget on each route, and allow a justified exception until Mapa is lazy-split), or adjust the target to something realistic for the first build while committing to incremental reductions. |

## 4. Unrealistic Acceptance Criteria

| # | Acceptance Criterion | Reference | Suggested Fix |
|---|---|---|---|
| 1 | **W0: "Eager JS < 150 KB gz" is extremely aggressive relative to current bundle.** Current is ~389 KB gz (01 §3.3). Achieving <150 KB gz requires lazy-loading MapLibre (which is a major chunk), splitting all four views into routes, moving pdf.js/html-to-image to dynamic imports, and pruning deps. Stating this as a flat acceptance without a route-based budget or staged target risks making the task unachievable as written. | PLAN.md: W0; 01-app-audit.md: §3.3 | Make the budget route-aware: e.g. "Salidas/Carrito/Programa initial route eager JS ≤ 120 KB gz; Mapa route lazy-loaded (separately tracked); overall CSS ≤ 25 KB gz. CI enforces per-route budgets and fails if any route exceeds its limit." Alternatively, set an intermediate target for W0 shell (without MapLibre) and a separate target for W2 when MapLibre loads. |
| 2 | **W2: "60 fps pan on a mid-range Android" as a hard acceptance.** 01 §3.2 and 02 §3 note MapLibre GL JS in WebView is the weakest on low-end Android; 02 explicitly lists this as a switch trigger (if <30 fps or cold start >3s, go to Expo). Declaring 60 fps as an unconditional acceptance is unrealistic without the explicit fallback path. | PLAN.md: W2, D1; 02-mobile-stack.md: §3, TL;DR; 01-app-audit.md: §3.3 | Rephrase as: "Target ≥ 60 fps pan/zoom on a mid-range Android device in the Capacitor spike; if measurements show sustained < 30 fps or cold start > 3s, treat the D1 switch trigger as hit and escalate to evaluate Expo (per §2 TL;DR). Record fps/cold-start numbers in the spike report." Make the acceptance conditional on the spike outcome. |
| 3 | **M0: "Switch triggers (D1) not hit" is underspecified.** D1 lists three concrete triggers (fps/cold start, offline vector packs/background location, Apple 4.2 rejections). M0 acceptance just says "not hit" with no required measurements, devices, or artifacts. This is not testable. | PLAN.md: M0, D1; 02-mobile-stack.md: TL;DR | Define M0 acceptance with concrete artifacts: test on specified devices (e.g., Moto G-class Android ≤3GB RAM, recent iPhone), record map pan fps (min/avg), cold start to first map frame (ms), compass behavior in WKWebView, pdf.js worker behavior, and geolocation prompts. Produce a short spike report (`docs/v2/research/06-capacitor-spike.md`) with pass/fail against each trigger and the final recommendation. |
| 4 | **F3: "The 13 skipped parser tests now run and pass" depends on committing sanitized fixtures.** This is correct in intent, but the acceptance doesn't specify that fixtures contain only fake data (no real names/PII), are deterministic, and work on a clean clone. 01 §4 notes fixtures were gitignored. Also the sanitized approach needs to be explicit to avoid reintroducing PII. | PLAN.md: F3; 01-app-audit.md: §4, §3.4 | Tighten F3 acceptance: "Commit sanitized `PdfItem[][]` JSON fixtures (containing only synthetic/fake names and no real PII) under version control; the 13 parser tests run and pass on a clean clone/CI (`npx vitest run --reporter=verbose` shows all 13 executed, not skipped); add a PII guard (e.g., grep for known name patterns or a small validator) in CI." |
| 5 | **W0: "tab switch < 100 ms" without defining measurement conditions.** Tab switching currently unmounts/remounts MapView (01 §1.1, §3.3), causing full context loss and slow switches. Achieving <100 ms with code splitting and route-level caching is possible, but the acceptance must specify whether this is first switch (cold) or subsequent (warm), and on what hardware/network. | PLAN.md: W0; 01-app-audit.md: §1.1, §3.3 | Clarify: "Subsequent tab switches complete within 100 ms on a mid-range Android (warm cache, JS already loaded), measured via Chrome DevTools Performance/React Profiler in the target build. First navigation to Mapa may be slower due to lazy chunk load but must show skeleton immediately (LCP for initial route < 1.5 s per §6)." |
| 6 | **Performance budgets in §6 lack enforcement scope.** §6 states "CI-enforced where possible" for JS/CSS budgets and lists APK/IPA sizes and cold start targets. But there's no explicit CI task or failure mode. Also "realtime only, no polling while connected" and "nothing runs in hidden tabs" are behavioral requirements not captured as testable acceptance criteria. | PLAN.md: §6; 01-app-audit.md: §3.3, §6 #7 | Add to F1: configure CI to enforce bundle-size budgets (per route) and fail on regression. Add to W0: acceptance criteria covering "pause realtime/pollers when document is hidden (`visibilitychange`) and when app goes to background; refetch on resume; no polling while realtime channel is connected." Include integration tests for these behaviors. |

**Summary:** PLAN.md is well-structured and largely aligned with the research. The main gaps are (1) specificity around the edit-sync edge cases and scheduler semantics that must be preserved, (2) making the aggressive bundle/map-performance targets conditional on the stated switch triggers, and (3) elevating P0 security items (signup state, legacy fallback removal, PII handling) to explicit, testable gates. Applying the suggested fixes will make the plan both more faithful to the audit and more realistically enforceable.
